VLOG #04 TEARDOWN • REAL-TIME CDC & OLAP ANALYTICS

Real-Time MongoDB to ClickHouse CDC Pipeline via Mongo Change Streams

Published: August 2026
9 min read summary
By Ashwinikumar Vishwakarma
Key Engineering Findings & Architecture Wins
Offloaded 100% Analytical Read Traffic: By routing all dashboard aggregation queries to an in-house ClickHouse cluster, MongoDB CPU usage dropped from 88% peak load down to a stable 12%.
Sub-100ms Event Sync Latency: MongoDB Change Streams (listening via watch()) stream real-time document mutations (insert, update, replace) into ClickHouse with a sub-100ms end-to-end propagation delay.
Deduplication via ReplacingMergeTree: Using ClickHouse's ReplacingMergeTree(updated_at) engine handles incoming document updates seamlessly without manual mutation deletes or table locks.

1. Problem Statement: WiredTiger Cache Eviction & Mongo Aggregation Bottlenecks

In high-velocity document stores (MongoDB running WiredTiger storage engine), executing multi-stage analytical aggregations (e.g. $unwind, $lookup, and large $group pipelines over 20+ million documents) forces WiredTiger to evict transactional index pages from RAM into swap files. During high-traffic events (25,000 requests/sec), analytical queries triggered cache eviction cascades, causing primary write lock waits to jump from 4 ms to 1,850 ms and leading to database connection pool exhaustion.

Rather than routing analytical read traffic to MongoDB secondary nodes (which still suffer from WiredTiger cache pressure), we engineered a non-blocking Change Data Capture (CDC) pipeline using MongoDB Change Streams and an in-house ClickHouse OLAP cluster. When transactional documents are inserted or updated in MongoDB, change events stream directly into ClickHouse. Analytical services query ClickHouse directly with sub-20ms latencies, completely isolating MongoDB from reporting traffic.

2. Architecture: Zero-Allocation Go Stream Listener

The CDC daemon opens a persistent Mongo stream using collection.Watch() with UpdateLookup mode. To process high-volume BSON streams without triggering Go GC pause spikes, the consumer reuses memory buffers via sync.Pool and batches up to 1,000 change records per ClickHouse TCP bulk block push (`max_insert_block_size = 100000`).

cdc_consumer.go (High-Performance Go Stream Listener) 
package main

import (
    "context"
    "log"
    "sync"

    "go.mongodb.org/mongo-driver/bson"
    "go.mongodb.org/mongo-driver/mongo"
    "go.mongodb.org/mongo-driver/mongo/options"
)

type ChangeEvent struct {
    OperationType string            `bson:"operationType"`
    FullDocument  bson.M            `bson:"fullDocument"`
    DocumentKey   struct{ ID string `bson:"_id"` } `bson:"documentKey"`
}

var rowPool = sync.Pool{
    New: func() any { return new(ClickHouseRow) },
}

func StreamToClickHouse(ctx context.Context, collection *mongo.Collection, chClient *ClickHouseClient) {
    opts := options.ChangeStream().SetFullDocument(options.UpdateLookup)
    stream, err := collection.Watch(ctx, mongo.Pipeline{}, opts)
    if err != nil {
        log.Fatalf("Failed to open Mongo change stream: %v", err)
    }
    defer stream.Close(ctx)

    batch := make([]*ClickHouseRow, 0, 1000)

    for stream.Next(ctx) {
        var event ChangeEvent
        if err := stream.Decode(&event); err != nil {
            continue
        }

        // Fetch recycled allocation from sync.Pool to eliminate GC pressure
        row := rowPool.Get().(*ClickHouseRow)
        row.MapFromBSON(event.DocumentKey.ID, event.FullDocument, event.OperationType)
        batch = append(batch, row)

        if len(batch) >= 1000 {
            chClient.BulkInsertRows("default.order_analytics", batch)
            for _, r := range batch {
                rowPool.Put(r)
            }
            batch = batch[:0]
        }
    }
}

3. ClickHouse Deduplication via ReplacingMergeTree

Document mutations in MongoDB are seamlessly synchronized to ClickHouse without issuing expensive DELETE or ALTER TABLE UPDATE mutations. ClickHouse's ReplacingMergeTree(updated_at) engine automatically merges updated rows in background compaction cycles:

clickhouse_schema.sql 
-- ClickHouse Target Table with Background Deduplication
CREATE TABLE default.order_analytics (
    order_id String,
    customer_id UInt64,
    order_status String,
    total_amount Decimal(18, 4),
    item_count UInt32,
    updated_at DateTime,
    is_deleted UInt8 DEFAULT 0
) ENGINE = ReplacingMergeTree(updated_at)
PRIMARY KEY (customer_id)
ORDER BY (customer_id, order_id);

-- High-speed analytical query reading latest document state from ClickHouse FINAL view
SELECT 
    order_status,
    count(DISTINCT customer_id) AS unique_customers,
    sum(total_amount) AS gross_revenue
FROM default.order_analytics FINAL
WHERE updated_at >= NOW() - INTERVAL 24 HOUR
GROUP BY order_status;

5. Production Lessons Learned

1. Oplog Retention Window: Ensure MongoDB oplog size is configured large enough (`oplogSizeMB: 50000`) so that if the CDC daemon pauses for maintenance, the resume token remains valid without forcing a full snapshot resync.

2. ReplacingMergeTree FINAL Clause Optimization: In ClickHouse version 23+, using FINAL in aggregations executes multithreaded deduplication efficiently across data parts without locking table operations.
